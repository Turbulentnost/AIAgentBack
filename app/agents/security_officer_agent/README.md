# Агент сотрудника службы безопасности (`security_officer_agent`)

Ролевой ИИ-агент контура №3 «Закупка и выбор поставщика». ТЗ: **ТЗ-АГТ-СБ-001**.
Реестр ролевых агентов — строка 25. Уровень автономности **У1** (У2 — уведомления/маршрутизация).
Контур primary №3, secondary №4. Нормативная база — **СТО-28-020 «Закупки» (версия 07)**.

> Статус: **архитектура (скелет)**. Внешние обращения (1С:ERP, RAG, LLM Gateway, внешние
> реестры, оркестратор) — мок-заглушки `app.platform_sdk`. Боевые подключения не выполнены
> (`TODO(integration)`).

## Назначение
Контрольный агент проверки контрагента: идентификация (Ф1) → сбор сведений из 1С, официальных
реестров, истории и связанности (Ф2, параллельные проверки) → сопоставление с обязательными
критериями (Ф3) → оценка уровня риска (Ф4) → проект заключения: согласование / условия допуска
/ отказ (Ф5). Агент формирует ТОЛЬКО проект заключения; утверждение, блокировка контрагента и
финансовые решения — за человеком.

## Функционал
Функциональные блоки выведены из должности «Сотрудник службы безопасности» (реестр, строка 25)
и шага 2.8 СТО-28-020 (версия 07). **Контрольный** агент проверки контрагента; триггеры:
новый поставщик, высокий риск, изменение условий, стадия договора. В контуре №4 заключение
обязательно для одноразового исключения до 10 000 ₽ (совместно с финансовым директором).

| Блок | Функция | Содержание |
|---|---|---|
| **Ф1** | Идентификация контрагента | Нормализация ИНН/ОГРН/наименования; поиск карточки в 1С; признак «новый контрагент». При неоднозначной идентификации — возврат закупщику, проверка не выполняется |
| **Ф2** | Сбор сведений (параллельно) | `check_registry_1c` (карточка, договоры, взаиморасчёты), `check_external_sources` (официальные реестры через интеграционный слой), `check_history` (исполнение, претензии), `check_affiliation` (связанность, конфликт интересов). Ошибка одного источника не останавливает проверку |
| **Ф3** | Сопоставление с критериями | Обязательные критерии из конфигурации арендатора; отметка покрытия; `source_reference` по каждому. При покрытии < 100% заключение **не выдаётся** |
| **Ф4** | Оценка уровня риска | Расчёт risk_level (низкий/средний/высокий); перечень факторов с источником и весом; учёт предусмотренных исключений; контроль ложных срабатываний (≤ 5%) |
| **Ф5** | Формирование заключения по контрагенту | Проект «ОТКАЗ» (высокий риск) / «УСЛОВИЯ ДОПУСКА» (средний: предоплата, обеспечение, лимит, сокращённый срок) / «СОГЛАСОВАНИЕ» (низкий); фиксация вердикта и уровня риска после утверждения |

**Типы задач (task_type):** `new_supplier_check` · `periodic_recheck` · `contract_check` · `exception_check`.

**За человеком:** утверждение заключения (сотрудник СБ; при критических факторах — руководитель
СБ); блокировка контрагента в 1С; юридическая проверка договора (агент юрслужбы); финансовое
решение по исключению до 10 000 ₽ (ФД + СБ совместно); оперативно-розыскные действия;
обработка ПДн сверх объёма проверки.

## Граф (nodes/)
`validate_input` → [невалидно → `assess_confidence`] → `normalize_counterparty`
- неоднозначная идентификация (нет ИНН / несколько карточек / расхождение) →
  `request_details` → `assess_confidence` (заключение не выдаётся)
- иначе → `check_registry_1c` → `check_external_sources` → `check_history` →
  `check_affiliation` → `map_to_criteria`
  - покрытие критериев < 100% → `list_gaps` → `assess_confidence`
  - иначе → `risk_scoring`
    - high → `draft_conclusion_reject`
    - medium → `draft_conclusion_conditional`
    - low → `draft_conclusion_approve`
  → `human_approve` (HITL) → `write_counterparty_verdict` → `assess_confidence`

Все ветви сходятся: `assess_confidence` → `emit_result` → END.

Узлы `check_*` — параллельные проверки Ф2 («инструмент / параллельно»). В мини-runtime собраны
последовательной цепочкой; в проде — один суперштаг LangGraph (fan-out / fan-in). Ошибка одного
источника не роняет граф — формируется частичный результат с понижением уверенности (T8).


## Ключевые ограничения
- Заключение не выдаётся при неоднозначной идентификации или покрытии критериев < 100% (K1, K6).
- Фиксация вердикта в 1С (`erp.write_counterparty_verdict`) — по белому списку и ТОЛЬКО после
  узла `human_approve` (`write_gate`, `write=True, hitl_passed=True`).
- Каждый фактор риска — со ссылкой на источник, датой обращения и статусом надёжности (K5).
- Персональные данные — только в объёме проверки; маскирование ПДн на уровне LLM Gateway
  (`mask_pii=True`).
- Guardrail-KPI **K3** «Доля необоснованных блокировок безопасных контрагентов» (≤ 5%): при
  нарушении порога — автоматическое понижение уровня автономности (`on_breach: downgrade_autonomy`).
