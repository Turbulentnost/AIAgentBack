# Агент начальника ОМТО (`omto_head_agent`)

Управляющий (надзорный) ролевой ИИ-агент контура №3 «Закупка и выбор поставщика».
ТЗ: **ТЗ-АГТ-ОМТО-НАЧ-001**. Реестр ролевых агентов — строка 15. Уровень автономности
**У1** (У2 — уведомления/маршрутизация). Владелец процесса: Начальник ОМТО; подотчётность:
Начальник службы логистики. Контуры: primary №3; secondary №4/№5. Нормативы: СТО-28-020
(версия 07), СТО-10-095.

> Статус: **архитектура (скелет)**. Внешние обращения (1С:ERP, RAG, LLM, оркестратор,
> сквозной агент качества данных) — мок-заглушки `app.platform_sdk`. Боевые подключения не
> выполнены (`TODO(integration)`).

## Назначение
Агент НЕ исполняет закупочные операции — он надзирает за их своевременностью и корректностью
и формирует ТОЛЬКО проекты: контроль распределения заявок (Ф1) → нормативные сроки закупки
(Ф2) → отклонения цены (Ф3) → поставка и претензии (Ф4) → решения/эскалации (Ф5) →
регламентная отчётность контура (Ф6). Отчёты (ежедневный, сводка, карточка рисков),
проекты решений и эскалации публикуются только после подтверждения человеком.

## Функционал
Функциональные блоки выведены из должности «Начальник ОМТО» (реестр, строка 15) и
процессных шагов СТО-28-020 (версия 07), СТО-10-095. Роль — **надзорная**: агент не исполняет
закупочные операции, а контролирует их и формирует проекты решений, эскалаций и отчётности.

| Блок | Функция | Содержание |
|---|---|---|
| **Ф1** | Контроль распределения заявок | Каждая позиция распределена ответственному в нормативный срок (шаг 2.1); при просрочке — сигнал агенту заместителя, при повторе — проект эскалации |
| **Ф2** | Контроль нормативных сроков закупки | Прохождение задач по этапам КТ2–КТ3; предупреждение *до* нарушения срока, а не по факту; доля просроченных задач |
| **Ф3** | Контроль отклонений цены | Соответствие цены проектной и сроку её действия; наличие проекта служебной записки и 2/3 сопоставимых предложений (шаг 3.3) |
| **Ф4** | Контроль поставки и претензий | Статусы счёта/оплаты/отгрузки/доставки; расхождение прогнозной и подтверждённой даты; своевременность претензий; влияние на производственный план (через оркестратор) |
| **Ф5** | Решения и эскалации | Классификация critical / major / minor; при critical — эскалация начальнику службы логистики + карточка критических рисков Операционному директору; контроль закрытия корректирующих действий в срок |
| **Ф6** | Отчётность контура | Ежедневный отчёт начальнику ОМТО, оперативная сводка начальнику службы логистики, карточка рисков ОД — как проекты, публикуются после подтверждения |

**Типы задач (task_type):** `periodic_control` · `case_review` · `price_deviation_review` · `daily_report`.

**За человеком:** утверждение назначения ответственного, согласование СЗ на цену и approval token,
утверждение нового/рискового поставщика, проведение документов в 1С и внешняя коммуникация,
финансовые решения и изменение бюджета.

## Граф (nodes/) — единый поток (TABLE 7)
`validate_input` → (невалидная задача → `assess_confidence`) → `load_context_1c` →
`data_quality_check` → `check_assignment_sla` → `check_procurement_sla` →
`check_price_deviation` → `check_delivery_deviation` → `check_claims` → `aggregate_findings`
→ `classify_severity` → `assess_confidence` →
- есть critical → `draft_escalation`
- иначе → `draft_decision_card`

→ `build_daily_report` → `human_review` (HITL) → `emit_result` → END.

Проверки `check_*` в ТЗ помечены «параллельно»: в проде выполняются в рамках ОДНОГО
суперштага LangGraph (ошибка одного источника не роняет граф, T8); в мини-runtime — цепочка.
`build_daily_report` формирует проект отчёта во всех ветках; для `task_type=daily_report`
это основной выход.

## Ключевые ограничения
- Роль надзорная: агент формирует проекты, но не утверждает назначения, СЗ, поставщиков и
  не проводит документы в 1С:ERP.
- Запись в 1С (`erp.write_decision`) — только по белому списку и после точки HITL
  (`write_gate`); фиксируется в `emit_result` c `hitl_passed=True`.
- Каждый существенный вывод — со ссылкой на источник (K5). critical — уверенность не выше
  medium (confidence.yaml).
