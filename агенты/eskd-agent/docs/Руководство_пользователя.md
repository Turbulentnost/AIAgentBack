## 1. Назначение системы

**ESKD Agent** (в документации ТЗ — «ПО ЕСКД-Контроль») предназначено для автоматической проверки конструкторской документации (КД) на соответствие требованиям ЕСКД и действующим ГОСТ.

Система выполняет:

- загрузку и предобработку файлов КД (PDF, чертежи, комплекты);
- автоматический анализ листов с помощью модели искусственного интеллекта;
- формирование структурированного протокола с указанием нарушений по ГОСТ;
- сохранение истории проверок и версий комплектов;
- ручную разметку замечаний сотрудниками ОТК и нормоконтроля;
- ведение базы знаний проверенных документов;
- интеграцию с корпоративными системами (PDM/PLM, 1С ERP, СЭД, Active Directory) через программные интерфейсы.

Согласно ТЗ (п. 4.8.1), система обеспечивает **совместимость** с ИТ-средой предприятия и **интеграцию** — автоматический обмен данными без повторного ручного ввода.

### Как работает проверка (кратко)

```
Файл КД → предобработка (конвертация в изображения листов)
        → анализ каждого листа (ИИ)
        → проверка правил по комплекту (сквозные замечания)
        → протокол по 8 ГОСТ → сохранение в «Историю»
```

При повторной проверке того же файла система может использовать сохранённую **разметку** или **результат из базы знаний** без повторного вызова ИИ.

## 2. Кому предназначено

| Роль | Основные задачи в системе |
|------|---------------------------|
| **Конструктор** | Предварительная проверка чертежей перед передачей в PDM; просмотр замечаний |
| **Сотрудник ОТК** | Запуск проверок, разметка, подтверждение записей в базе знаний |
| **Нормоконтролёр** | Контроль комплектов, работа с историей, интеграция с СЭД |
| **Руководитель** | Просмотр статистики нарушений, готовности КД |
| **Администратор / интегратор** | Журнал интеграций, настройка обмена с PDM и 1С |
| **Аудитор** | Просмотр истории проверок и журнала обмена |

## 3. Доступ к системе

### Адрес веб-интерфейса

По умолчанию интерфейс доступен по адресам:

| Среда | URL |
|-------|-----|
| Локально | `http://127.0.0.1:3000` или `http://127.0.0.1:8000` |
| В локальной сети | `http://<IP-сервера>:8000` |

Точный адрес определяет администратор при развёртывании.

### Вход в систему

В промышленной среде предусмотрена интеграция с **Active Directory / LDAP** (п. 4.8.7 ТЗ): пользователь входит под корпоративной учётной записью, роли назначаются по группам AD.

В режиме разработки и тестирования (`AUTH_MODE=dev`) в правом верхнем углу интерфейса доступен **селектор сотрудника ОТК**. Выберите своё имя перед сохранением проверок и подтверждением записей в базе знаний — система запишет, кто выполнил действие.

Тестовые пользователи по умолчанию: `otk.ivanov`, `otk.petrova`.

### Индикатор готовности

На вкладке «Проверка» в правом верхнем углу отображается статус модели ИИ:

| Индикатор | Значение |
|-----------|----------|
| **Модель готова** (зелёный) | Сервис анализа доступен, можно запускать новые проверки |
| **Модель загружается** (серый) | Сервис ещё не готов — дождитесь готовности |
| **Анализ…** (жёлтый) | Идёт текущая проверка |

Если модель недоступна, но для загруженного файла есть сохранённая разметка или результат в базе знаний, проверку всё равно можно выполнить — ИИ вызываться не будет.

## 4. Роли и права пользователей

Согласно ТЗ (п. 8, 4.8.7), роли сопоставляются группам Active Directory:

| Группа AD | Роль в системе | Возможности |
|-----------|----------------|-------------|
| `ESKD_Administrators` | Администратор | Полный доступ, API-ключи, настройка интеграций |
| `ESKD_NormControl` | Нормоконтролёр | Проверки, журнал, передача в СЭД |
| `ESKD_OTK` | ОТК | Проверки, разметка, база знаний, журнал |
| `ESKD_Designers` | Конструктор | Запуск и просмотр проверок |
| `ESKD_Managers` | Руководитель | Просмотр результатов, ERP-данные |
| `ESKD_Auditors` | Аудитор | Только чтение истории и журнала |

**Важно для пользователя:** все вкладки веб-интерфейса видны всем пользователям. Разграничение прав строго применяется к **интеграционным API** (автоматический обмен с PDM, 1С и т.д.). При работе только через браузер выбор сотрудника ОТК в шапке определяет, от чьего имени сохраняются проверки и подтверждения.

## 5. Обзор интерфейса

Интерфейс состоит из шести вкладок в верхней панели навигации:

| Вкладка | Назначение |
|---------|------------|
| **Проверка** | Загрузка КД и запуск автоматической проверки |
| **История** | Архив всех проверок с детализацией по листам |
| **Разметка** | Ручная фиксация нарушений ГОСТ по листам |
| **База знаний** | Каталог проверенных документов |
| **Статистика** | Частота нарушений по ГОСТ в разметке |
| **Интеграции** | Журнал автоматического обмена с внешними системами |

В правой части шапки — **селектор сотрудника ОТК** (в dev-режиме).

## 6. Вкладка «Проверка»

### 6.1. Назначение

Основной рабочий экран для автоматической проверки КД. Соответствует сценарию «ручная загрузка документа» (Этап 1 интеграции по ТЗ) и используется также при работе без PDM.

### 6.2. Загрузка файлов

1. Перетащите файлы в область загрузки **или** нажмите для выбора.
2. Допустимые форматы: PDF, PNG, JPG/JPEG, ZIP-комплект, а также DOCX, XLSX, DWG, DXF, CDW и др. (см. [раздел 13](#13-поддерживаемые-форматы-файлов)).
3. Можно загрузить **один файл** или **несколько файлов** (комплект).
4. При загрузке одного файла система автоматически ищет его в базе знаний, истории и разметке.

**Поле «Обозначение»** — необязательное. Укажите обозначение документа (например, `UFG-700-16.02.00.000`), если оно известно. Это помогает при сверке и фильтрации в истории.

### 6.3. Выбор листов для проверки

Для многостраничных PDF доступны режимы:

| Режим | Описание |
|-------|----------|
| **Все листы** | Проверяется весь документ |
| **Один лист** | Укажите номер листа |
| **Диапазон** | Укажите «с … по …» |
| **Список** | Перечислите номера через запятую (например, `1,3,5`) |

### 6.4. Запуск и ход проверки

1. Нажмите **«Запустить проверку»**.
2. Наблюдайте прогресс:
   - **Конвертация** — PDF/DWG и др. преобразуются в изображения листов;
   - **VLM: лист N/M** — анализ каждого листа моделью (обычно 15–30 с на лист при облачной модели, дольше при локальной GPU);
   - **Проверка комплекта** — сквозные правила по всему комплекту (несоответствия между листами, состав комплекта).
3. По завершении отображается **итоговый протокол** с разбором по каждому листу.

**Отмена:** кнопка «Остановить» прерывает текущую проверку.

### 6.5. Результат проверки

Для каждого листа показывается:

- **Элементы** — реквизиты штампа, спецификация, виды и т.д. с отметкой ✓/✗;
- **Позиции спецификации** — таблица BOM с порядком и читаемостью;
- **Ошибки и предупреждения** — с указанием ГОСТ и текстом замечания;
- **Сводка по 8 ГОСТ** — какие стандарты пройдены, где есть замечания или ошибки.

При проверке **комплекта** дополнительно выводятся **сквозные замечания** (`package_errors`) — нарушения, видимые только при анализе нескольких листов вместе (расхождение обозначений, нумерация листов, состав комплекта).

### 6.6. Кэширование (без повторного вызова ИИ)

Если для файла уже есть данные, система не вызывает модель повторно:

| Источник | Сообщение при запуске |
|----------|----------------------|
| Разметка | «Найдена сохранённая разметка — проверка ИИ не выполняется» |
| История / база знаний | «Найден сохранённый результат проверки — ИИ не вызывается» |

Это соответствует требованию ТЗ об устойчивости: при недоступности модели результат может быть получен из ранее сохранённых данных.

### 6.7. Сохранение в историю

Каждая проверка, запущенная через интерфейс, автоматически сохраняется во вкладке **«История»**. Проверки, идущие в данный момент, отображаются со статусом **«В процессе»** и обновляются по мере обработки листов.

## 7. Вкладка «История»

### 7.1. Назначение

Хранение всех проверок с метаданными файла и результатами. Соответствует требованиям ТЗ о сохранении истории проверок всех версий документа (п. 4.8.4) и связке «документ → версия → проверка → протокол» (п. 4.8.6).

### 7.2. Список проверок

Таблица содержит:

| Колонка | Описание |
|---------|----------|
| **Дата** | Дата и время запуска |
| **Статус** | «В процессе», «Готово», «Отменено» |
| **Файл** | Имя загруженного файла |
| **ГОСТ** | Компактная сводка по 8 стандартам (✓ / ⚠ / ✗) |
| **Ошибки** | Общее число ошибок и предупреждений |

**Фильтры:** по имени файла и по обозначению.

Проверки со статусом «В процессе» обновляются автоматически каждые несколько секунд — виден прогресс `обработано/всего` листов.

### 7.3. Детали проверки

Нажмите строку в списке, чтобы открыть детали:

- **Сводка по 8 ГОСТ** — форма с пройденными стандартами, замечаниями и ошибками (тот же формат, что в разметке и базе знаний);
- **Разбор по листам** — полный протокол каждого листа;
- **Версии комплекта** — если документ проверялся повторно, отображаются версии и связь между ними;
- **Журнал изменений** — что изменилось между версиями проверки.

### 7.4. Контроль актуальности (по ТЗ)

При изменении файла (другая контрольная сумма) результат предыдущей проверки считается **неактуальным**. При повторной загрузке изменённого файла создаётся **новая версия** результата; старая сохраняется в истории для аудита.

## 8. Вкладка «Разметка»

### 8.1. Назначение

Ручная фиксация нарушений ГОСТ сотрудником ОТК или нормоконтролёром. Используется для:

- документирования замечаний при переделке;
- обучения и уточнения базы знаний;
- получения результата проверки без ИИ (при наличии разметки).

### 8.2. Загрузка документа

1. Нажмите **«Загрузить»** и выберите PDF или JPG.
2. Укажите **обозначение** (рекомендуется).
3. Если документ уже есть в системе, появится предложение **открыть существующий** или загрузить заново.

После загрузки отображается **превью листов** документа — изображение каждой страницы для визуального контроля.

### 8.3. Разметка по листам

Для **каждого листа** отдельно:

1. Выберите лист в навигации (номера листов с замечаниями подсвечиваются).
2. Для каждого из **8 ГОСТ** укажите статус:
   - **ОК** — нарушений нет;
   - **Замечание** — некритичное отклонение;
   - **Ошибка** — критичное нарушение.
3. При необходимости добавьте **текстовую заметку** к конкретному ГОСТ.
4. В поле **«Отчёт о проблеме»** опишите общую проблему по листу или документу.

Нажмите **«Сохранить»** — разметка записывается в базу данных.

### 8.4. Подтверждение в базе знаний

После сохранения разметки доступна кнопка **«Подтвердить в базе знаний»**. Подтверждение фиксирует:

- кто из сотрудников ОТК проверил документ;
- дату и время подтверждения (`human_verified_at`).

Подтверждённая запись используется как достоверный источник при повторных проверках того же файла.

## 9. Вкладка «База знаний»

### 9.1. Назначение

Единый каталог документов, по которым выполнена автоматическая проверка и/или ручная разметка. Соответствует идее ТЗ о том, что система проверки не дублирует реестр PDM, но хранит **техническую копию** и результаты проверки для повторного использования.

### 9.2. Каталог

Каждая **плитка** — один документ (файл или комплект). Отображается:

- имя файла и обозначение;
- источник данных: **ИИ**, **разметка**, **оба**;
- статус: **проверен** (подтверждён ОТК) или **не проверен**;
- дата последней проверки или разметки;
- сводка по ГОСТ.

**Поиск** — по имени файла и обозначению.  
**Фильтр** — все / только проверенные / только непроверенные.

### 9.3. Действия с записью

| Действие | Описание |
|----------|----------|
| **Открыть в разметке** | Переход на вкладку «Разметка» с этим документом |
| **Подтвердить** | Фиксация human verify сотрудником ОТК |
| **Удалить** | Удаление записи вместе со связанной разметкой и проверками (необратимо, двухшаговое подтверждение) |

### 9.4. Использование при проверке

При загрузке на вкладке «Проверка» файла, который есть в базе знаний, система автоматически предложит использовать сохранённый результат — **без повторного анализа ИИ**.

## 10. Вкладка «Статистика»

### 10.1. Назначение

Аналитика по **ручной разметке**: какие стандарты чаще всего отмечаются как нарушенные при переделках документов.

### 10.2. Таблица

| Колонка | Описание |
|---------|----------|
| **ГОСТ** | Код и название стандарта |
| **Ошибки** | Сколько раз отмечено как «ошибка» |
| **Замечания** | Сколько раз отмечено как «замечание» |
| **Всего** | Сумма нарушений по этому ГОСТ |
| **После проверки ИИ** | Нарушения, зафиксированные в разметке после того, как ИИ не нашёл проблему на этом ГОСТ |

Если данных нет — создайте разметку на вкладке «Разметка».

## 11. Вкладка «Интеграции»

### 11.1. Назначение

**Журнал интеграционного обмена** (п. 4.8.12 ТЗ) — аудит автоматических операций между ESKD Agent и внешними системами (PDM, 1С, СЭД, REST-клиенты).

### 11.2. Что отображается

| Поле | Описание |
|------|----------|
| **Время** | Дата и время операции |
| **Отправитель** | Система-источник запроса |
| **Операция** | Тип действия (создание проверки, webhook, ERP и т.д.) |
| **Результат** | Успех / ошибка |
| **request_id** | Сквозной идентификатор запроса |
| **Обозначение** | Обозначение документа, если передано |

**Фильтры:** по `request_id` и `source_system`.

### 11.3. Когда журнал пуст

Журнал заполняется только при **автоматическом обмене** через интеграционные API (`/api/v1/checks`, webhooks, файловый обмен). Если вы работаете **только через браузер** (ручная загрузка на вкладке «Проверка»), записей в журнале интеграций, как правило, **не будет** — это нормально. Такие проверки сохраняются во вкладке **«История»**.

В шапке журнала отображаются **текущий пользователь** и **роли** (для контроля прав доступа к API).

## 12. Справочник по 8 ГОСТ

Система группирует все замечания по **восьми ключевым стандартам** ЕСКД. Формат единый во всех разделах: проверка, история, разметка, база знаний.

| Код | Стандарт | Что проверяется |
|-----|----------|-----------------|
| **2.104** | ГОСТ Р 2.104-2023 | Штамп: наименование, лист/листов, масштаб, подписи (Разраб., Пров., Н.контр., Утв.) |
| **2.201** | ГОСТ Р 2.201-2023 | Обозначение документа: структура, опечатки, согласованность между зонами |
| **2.105** | ГОСТ 2.105 | Спецификация (BOM): позиции, порядок, количество, соответствие выноскам |
| **2.109** | ГОСТ Р 2.109-2023 | Чертежи: виды, разрезы, выноски позиций, посторонние объекты |
| **2.503** | ГОСТ Р 2.503-2023 | Изменения: графы «Изм.», «Ред.», даты, номера извещений |
| **2.316** | ГОСТ Р 2.316-2023 | Технические требования и надписи на поле чертежа |
| **2.308** | ГОСТ Р 2.308-2023 | Геометрические допуски и размерные рамки |
| **2.301** | ГОСТ 2.301 | Форматы листов, масштаб изображения |

### Статусы в сводке

| Обозначение | Значение |
|-------------|----------|
| ✓ / «ОК» | Нарушений по этому ГОСТ не выявлено |
| ⚠ «Замечание» | Некритичное отклонение (например, нечитаемое поле) |
| ✗ «Ошибка» | Критичное нарушение (например, расхождение обозначений, пропуск подписи) |

### Принцип работы ИИ

Модель анализирует **изображение листа**. Если требование ГОСТ **не видно** на листе (например, технические требования на другом листе комплекта), ошибка **не создаётся** — это соответствует методике проверки и снижает ложные срабатывания.

## 13. Поддерживаемые форматы файлов

| Формат | Назначение |
|--------|------------|
| **PDF** | Основной формат для проверки (сканы и векторные PDF) |
| **PNG, JPG, JPEG** | Отдельные листы чертежей |
| **ZIP** | Комплект нескольких файлов |
| **DOCX, XLSX** | Текстовые и табличные документы (с конвертацией) |
| **DWG, DXF, CDW** | Чертежи CAD (с конвертацией в изображения) |
| **SPW, XML** | Специализированные форматы (при наличии конвертера) |

**Ограничения:**

- максимальный размер загрузки — **200 МБ** (настраивается администратором);
- максимальное число листов за одну проверку — **50** (настраивается);
- PDF без текстового слоя обрабатываются как изображения (OCR/VLM).

## 14. Типовые сценарии работы

### 14.1. Конструктор: проверка перед передачей в PDM

1. Экспортируйте чертёж в PDF из CAD.
2. Откройте вкладку **«Проверка»**, загрузите файл.
3. Дождитесь протокола, устраните замечания в CAD.
4. Повторите проверку — в истории появится новая версия.

*На последующих этапах (по ТЗ, п. 14) проверка может запускаться **из CAD-плагина** или **автоматически из PDM** при смене статуса документа.*

### 14.2. ОТК: проверка поступившего комплекта

1. Получите PDF-комплект (или ZIP).
2. Запустите проверку на вкладке **«Проверка»** (все листы).
3. Изучите протокол: сводку по 8 ГОСТ и детали по листам.
4. При необходимости откройте **«Историю»** для архивирования и передачи результатов.

### 14.3. ОТК: разметка при переделке

1. Откройте **«Разметка»**, загрузите документ.
2. Пройдите по листам, отметьте нарушенные ГОСТ.
3. Сохраните и **подтвердите в базе знаний**.
4. Статистика на вкладке **«Статистика»** обновится автоматически.

### 14.4. Нормоконтролёр: повторная проверка после исправлений

1. Получите новую версию файла из PDM (или от конструктора).
2. Загрузите на **«Проверка»**.
3. Система создаст **новую версию** в истории; сравните с предыдущей через **«Журнал изменений»**.
4. При отсутствии критических ошибок документ можно передавать на согласование.

*По ТЗ (п. 4.8.4): при критических нарушениях PDM **блокирует** переход в статус «На согласовании» — это настраивается на стороне PDM при интеграции.*

### 14.5. Работа без модели ИИ

Если сервис анализа недоступен:

1. Убедитесь, что документ есть в **разметке** или **базе знаний**.
2. Загрузите тот же файл на **«Проверка»**.
3. Система вернёт сохранённый результат без вызова ИИ.

## 15. Интеграция с корпоративными системами

Раздел описывает, как система взаимодействует с ИТ-ландшафтом предприятия с точки зрения пользователя. Техническая документация для интеграторов — в каталоге `docs/integration/`.

### 15.1. Общая схема (по ТЗ, п. 2)

```
CAD → PDM/PLM → Интеграционный шлюз → ESKD Agent → результат → PDM / 1С / СЭД
```

Пользователь **не работает с шлюзом напрямую** — он продолжает работать в PDM, 1С или веб-интерфейсе ESKD Agent в зависимости от сценария.

### 15.2. PDM/PLM (основной сценарий)

| Этап | Действие пользователя | Действие системы |
|------|----------------------|------------------|
| 1 | Конструктор завершает документ, переводит в статус «Готов к проверке ЕСКД» | PDM автоматически отправляет файл и метаданные |
| 2 | — | ESKD Agent выполняет проверку |
| 3 | Нормоконтролёр видит результат в карточке PDM | В PDM возвращаются статус, число замечаний, ссылка на протокол |
| 4 | При критических ошибках — исправление и повторная отправка | Создаётся новая версия проверки; старая сохраняется в истории |

### 15.3. 1С ERP

1С получает **статус готовности КД** к производственному запуску, ссылку на протокол и сведения о критических замечаниях. Пользователь 1С видит, можно ли запускать изделие в производство без доработки документации.

### 15.4. СЭД и архив

После утверждения в СЭД передаются:

- итоговый протокол проверки;
- сведения о версии и контрольной сумме файла;
- дата проверки и пользователь;
- решение нормоконтролёра.

### 15.5. Active Directory

Единый вход под корпоративной учётной записью. Роли назначаются автоматически по группам AD (см. [раздел 4](#4-роли-и-права-пользователей)).

### 15.6. Этапы внедрения интеграции (п. 14 ТЗ)

| Этап | Что доступно пользователю |
|------|---------------------------|
| **1. Базовая интеграция** | Ручная загрузка, веб-интерфейс, история, PDF/JSON-протоколы, журнал обмена |
| **2. PDM/PLM** | Автозапуск из карточки КД, блокировка маршрута при критических ошибках |
| **3. 1С ERP** | Статус готовности КД в учётной системе |
| **4. CAD** | Команда «Проверить ЕСКД» в CAD, подсветка ошибок на чертеже |

## 16. Частые вопросы и решение проблем

### «Модель загружается» — проверка недоступна

**Причина:** сервис анализа (model API) не запущен или ещё загружается.  
**Решение:** обратитесь к администратору. Если для файла есть разметка или запись в базе знаний — проверку можно выполнить без модели.

### «Сеть: backend недоступен»

**Причина:** не отвечает сервер приложения (порт 8080).  
**Решение:** проверьте доступность сервера, обновите страницу. Не закрывайте вкладку во время длительной проверки.

### Проверка долго идёт на большом комплекте

**Норма:** каждый лист анализируется отдельно. Комплект из 28 листов может занимать **10–30 минут** и более в зависимости от конфигурации (облачная или локальная модель). Прогресс отображается на экране и во вкладке «История».

### Один лист с ошибкой «Connection timed out»

**Причина:** временный сбой связи с облачной моделью или перегрузка.  
**Решение:** повторите проверку только для проблемных листов (режим «Список») или перезапустите полную проверку.

### Результат ИИ не совпадает с мнением ОТК

Используйте **«Разметку»** для фиксации правильного результата и **подтвердите в базе знаний**. При следующей проверке того же файла будет использована разметка, а не ответ ИИ.

### В «Истории» пусто, хотя проверка была

**Причина:** проверка могла быть прервана (закрытие вкладки, перезапуск сервера) до сохранения.  
**Решение:** запустите проверку заново **из интерфейса** (не через внешние скрипты). Дождитесь статуса «Готово».

### «Журнал интеграций» пуст

Это **не ошибка**, если вы работаете только через браузер. Журнал относится к автоматическому M2M-обмену. Ваши проверки — во вкладке **«История»**.

### Изменил файл — старый протокол ещё виден

**По ТЗ:** при изменении файла (другая контрольная сумма) старый результат считается неактуальным, но **сохраняется в истории** для аудита. Актуальным является результат **последней** проверки новой версии файла.

## 17. Термины и сокращения

| Термин | Определение |
|--------|-------------|
| **ЕСКД** | Единая система конструкторской документации |
| **КД** | Конструкторская документация (чертежи, спецификации, текстовые документы) |
| **ГОСТ** | Государственный стандарт; в системе — 8 ключевых стандартов оформления КД |
| **ОТК** | Отдел технического контроля |
| **BOM** | Bill of Materials — спецификация (ведомость материалов) |
| **Обозначение** | Уникальный код документа (например, `UFG-700-16.02.00.000`) |
| **Комплект** | Набор связанных листов и файлов одного изделия |
| **VLM** | Vision-Language Model — модель анализа изображений чертежей |
| **Разметка** | Ручная фиксация нарушений ГОСТ сотрудником |
| **База знаний** | Каталог проверенных документов с результатами ИИ и разметки |
| **Human verify** | Подтверждение записи уполномоченным сотрудником ОТК |
| **PDM/PLM** | Система управления данными об изделии (источник версий КД) |
| **СЭД** | Система электронного документооборота |
| **M2M** | Machine-to-Machine — автоматический обмен между системами без участия человека |
| **Протокол** | Структурированный отчёт о результатах проверки (в UI, PDF или JSON) |
| **Ruleset** | Версия набора правил проверки ЕСКД, применённая при анализе |
